# Архитектура MVP

## Решение

Приложение строится как модульный монолит с четырьмя направленными слоями:

1. `domain` — граф компетенций, доказательства, профилирование и мэтчинг;
2. `application` — пользовательские сценарии и границы транзакций;
3. `infrastructure` — SQLite и адаптер входного контракта ФСП;
4. `web` — FastAPI, OpenAPI, роли, сессии и статический интерфейс.

Зависимости направлены внутрь: доменный код не импортирует FastAPI, SQLite или
код интерфейса. Отдельные сервисы не выделяются, пока у них нет независимой
нагрузки и жизненного цикла.

## Почему так

- FastAPI рекомендует разносить крупное приложение по модулям и роутерам, при
  этом сохраняя единое приложение: <https://fastapi.tiangolo.com/tutorial/bigger-applications/>.
- Изолированные доменные границы уменьшают радиус изменений и не требуют
  сетевого разделения: <https://martinfowler.com/articles/linking-modular-arch.html>.
- SQLite подходит для односерверного MVP с низкой конкуренцией записи и хранит
  данные рядом с приложением без отдельного процесса:
  <https://www.sqlite.org/whentouse.html>.

## Контексты

- **Каталог:** дисциплины, соревнования, навыки и связи между ними.
- **Доказательства:** результаты, роли, разряды, происхождение и уверенность.
- **Талант:** вычисляемый профиль, категории и грейд кандидата.
- **Подбор:** вакансии, критичность требований, политика доказательств, совпадения
  и приватные приглашения.
- **Доступ:** пользователь, подтверждение email, хэшированная сессия, роль и
  владение объектами.
- **Коммуникация:** приглашения и отклики с конечным автоматом статусов;
  контакт кандидата раскрывается только после его действия.

Контексты разделены модулями, но используют одну транзакционную БД. Это даёт
атомарный импорт результатов и простой резервный файл для демонстрации.

## Алгоритмический контракт

- уровень навыка — максимум силы релевантного результата, усиленный несколькими
  независимыми доказательствами;
- уверенность — объединённая надёжность источника, соревнования и результата;
- политика работодателя сначала фильтрует доказательства, затем рассчитывается
  профиль специально для вакансии;
- покрытие — среднее отношения подтверждённого уровня к требуемому с весом
  критичности; подтверждённый уровень учитывает доверие к доказательствам;
- итог совпадения состоит из 85% покрытия и 15% абсолютной подтверждённой силы,
  после чего умножается на `0.94` за каждый критичный пробел;
- разность графов сохраняет навыки, где требуемый уровень выше подтверждённого;
- целевой навык раскрывается в DAG по всем транзитивным пререквизитам; знание
  предка не считается знанием потомка;
- рекомендация соревнования максимизирует ожидаемое закрытие взвешенного
  дефицита при допустимой политике доказательств.

Итог ограничен диапазоном 0–100. Категория кандидата вычисляется по среднему
произведению уровня и уверенности навыков одной специализации; отображаемый
уровень `growing` / `confident` / `advanced` описывает только силу проверенного
профиля и не выдаётся за трудовой стаж или должностной грейд.

Все коэффициенты именованы, ограничены диапазоном и покрыты тестами. Ответ API
возвращает составляющие оценки, поэтому ранжирование можно объяснить без
обращения к логам или внешней модели.

Тест грейда — отдельный доказательный источник. Вариант детерминированно
собирается из эквивалентных семейств по blueprint специализации и грейда.
Порог подтверждения — `0.70`, рекомендация следующего грейда — от `0.875`;
неуспех никогда не понижает профиль автоматически. Изменение подтверждённого
грейда блокируется на 90 дней.

## Безопасность и будущие интеграции

Пароли и одноразовые коды хранятся как `scrypt`, session token — только как
SHA-256 digest; cookie `HttpOnly`, `SameSite=Strict`, а в HTTPS-режиме `Secure`.
Запись ограничена ролью и владельцем. FSP-sync имеет отдельный интеграционный
ключ и выключен без него. Будущий Keycloak добавляет OIDC-адаптер `subject → user`,
не меняя доменные ID. ATS подключается исходящими подписанными webhook-событиями
`invitation.accepted` и `application.*` с idempotency key.

Тестовый провайдер ФСП ID использует подписанный запрос и одноразовый код,
привязанный к пользовательской сессии. Это исполняемая граница будущего OIDC,
но не имитация доступа к производственной базе ФСП.

Текст вакансии или соревнования преобразуется только в узлы известного каталога.
Офлайн-правила остаются обязательным CPU-путём; YandexGPT — опциональный адаптер.
Его JSON проверяется и не может добавить неизвестную компетенцию.

## Эксплуатационные ограничения

- один процесс приложения на отдельном порту;
- CPU-only, без обязательных внешних сервисов;
- данные ФСП могут синхронизироваться из локального JSON;
- сервис, каталог, unit systemd и данные развёртываются отдельно от MetroGuard;
- существующие `/opt/metroguard`, `metroguard.service`, Nginx-конфигурация,
  сертификаты и задания не изменяются.

## Визуальная система

Интерфейс следует принципам Material 3 Expressive: насыщенные, но семантические
цветовые роли, контрастные скруглённые формы, гибкая типографическая шкала и
движение только для пояснения смены состояния. Ориентиры:

- <https://m3.material.io/>;
- <https://m3.material.io/styles/color/the-color-system>;
- <https://m3.material.io/styles/typography/applying-type>;
- <https://m3.material.io/styles/motion>.

Собственная палитра «Выготского» сочетает глубокий фиолетовый, графит, лайм и
коралловый акцент. UI не копирует Google и не выдаёт продукт за официальный
сервис ФСП или ЛЦТ. Знак ФСП извлечён без перерисовки из предоставленного
заказчиком шаблона презентации; происхождение данных дополнительно раскрывается
текстом и дисциплинами.
