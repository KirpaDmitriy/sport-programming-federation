# Сценарий демонстрации

Сценарий проверен на реализованном интерфейсе: локально (`pnpm mock` + `pnpm dev`) и на стенде
<https://188.166.88.183>. Данные стенда синтетические, письма не отправляются, код подтверждения на стенде —
`123456` (он показан рядом с полем кода). Состояние общее для всех посетителей и сбрасывается перезапуском сервиса.

Откройте три независимых окна браузера (например, обычное, приватное и другой браузер): кандидат, «Север Тех»,
«Вторая компания».

## 1. Новый кандидат

1. «Вход и регистрация» → роль «Кандидат» → новый адрес почты → «Получить код» → код → «Подтвердить и войти».
2. Открывается анкета. Отметьте «Согласен на обработку данных» и включите «Показывать профиль работодателям» —
   это два отдельных решения.
3. Заполните имя, отрасль, специализацию «Бэкенд», грейд для проверки «Джуниор», стек, стаж в месяцах, опыт и роль.
   «Сохранить анкету». ФСП ID не требуется.
4. «Подтвердить уровень» → практическая задача. Напишите код, на шаге «Объяснение» опишите решение.
   Статус «Черновик сохранён» появляется только после ответа сервера. «Отправить решение».
5. Результат: «Джуниор подтверждён», «Профиль обновлён автоматически». В обзоре появляется подтверждённый грейд и
   псевдоним для работодателей.

## 2. Повышение грейда кандидата №024 (как на макетах)

1. Войдите как `alexey@example.com`. Обзор: «Джуниор подтверждён», «Цель: Мидл», источники GitHub и ФСП.
2. «Источники»: найдено 12, обработано 11, в очереди 0, недоступно 1; репозитории с демо-пометкой; часы работы не
   измеряются. «Указать ФСП ID» → `FSP-DEMO-024` даёт синтетическое подтверждённое участие, любой другой ID —
   «Истории ФСП нет».
3. «Навыки» → «Граф» → PostgreSQL: «Есть свидетельства», «Для уровня «Мидл» нужна проверка», основание из GitHub.
4. «Начать проверку» → решение и объяснение → «Отправить решение» → «Мидл подтверждён», Было «Джуниор» → Теперь
   «Мидл». Rust и PostgreSQL подтверждены на уровне «Мидл», Redis остаётся пробелом.
5. «Скачать PDF» — PDF текущего профиля.

## 3. Работодатель «Север Тех»

1. Войдите как `hr@sever-tech.example` (роль «Работодатель»). «Потребности» → «Бэкенд-разработчик»: зарплата
   200 000 – 260 000 ₽/мес «До вычета налогов», обязательные Rust и PostgreSQL, желательные Docker и Redis,
   политика подтверждений по каждому требованию. Публикация вакансии не нужна.
2. «Сохранить и найти кандидатов» → рекомендации с объяснением: группы по обязательным требованиям, №018 —
   «Грейд подтверждён», но PostgreSQL требует проверки.
3. Подборка справа сохраняется на сервере. Выберите «Стек: PostgreSQL» — №018 пропадает из выдачи, но остаётся в
   подборке; закладки синхронны.
4. Откройте кандидата №024: обезличенный профиль, требования по пунктам, «Контакты и ссылки скрыты до согласия
   кандидата». «Пригласить кандидата» → предложение, снимок условий, контакт компании → «Отправить приглашение».

## 4. Решение кандидата и раскрытие

1. В окне кандидата: колокольчик или «Приглашения» → приглашение «Север Тех». До решения видны зарплата, описание
   компании и её контакт.
2. Оставьте отмеченными «Имя и фамилия», при желании снимите «Email» → «Принять и открыть контакты».
3. «Север Тех» обновляет профиль кандидата: видны ровно выбранные поля.
4. «Вторая компания» (`hr@second-company.example`) открывает того же кандидата — профиль по-прежнему обезличен.

## Короткие проверки

- Отклонение приглашения не открывает контакты; обе стороны видят статус «Отклонено».
- Отзыв приглашения компанией делает решение кандидата недоступным.
- Неудачное повышение и сбой оценивания сохраняют подтверждённый грейд (сценарии `assessment_failure` и
  `service_failure` в локальном режиме через кнопку «Демо»).
- Кандидат не может открыть кабинет работодателя: «Раздел недоступен».
