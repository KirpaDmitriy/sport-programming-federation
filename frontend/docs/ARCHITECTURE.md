# Frontend architecture

A static React SPA built by Vite. TanStack Router owns navigation and URL state, TanStack Query owns server state,
TanStack Form owns form state. All server data goes through one typed client generated from
[`../../contracts/openapi.json`](../../contracts/openapi.json). The browser never decides grades, eligibility,
matching, ranking or access: it renders what the API returns. API behavior is described in
[`../../contracts/API_INTEGRATION.md`](../../contracts/API_INTEGRATION.md).

## Layers

The code follows Feature-Sliced Design. Imports go only downward (`app → pages → widgets → features → entities →
shared`), slices of one layer do not import each other, and other layers reach a slice only through its `index.ts`.
`scripts/check-layers.ts` (part of `bun run lint`) enforces these rules and keeps test helpers out of production
code.

| Layer | Slices |
| --- | --- |
| `app` | `app.tsx` (query client and router wiring, global 401 handling), `router.tsx`, `query-client.ts`, `guards.ts`, `route-states.tsx`, file routes in `routes/`, global styles and tokens in `styles/` |
| `pages` | `login`; candidate: `candidate-onboarding`, `candidate-overview`, `candidate-profile`, `candidate-sources`, `candidate-skills`, `candidate-assessments`, `assessment-workspace`, `assessment-result`, `candidate-invitations`, `candidate-invitation`, `candidate-settings`; employer: `employer-needs`, `employer-need-editor`, `employer-candidates`, `employer-candidate`, `employer-shortlists`, `employer-shortlist`, `employer-invitations`, `employer-company`, `employer-settings` |
| `widgets` | `app-shell` (navigation, account menu, «Демо» dialog, dev controls), `competence-graph` (React Flow), `shortlist-panel`, `assessment-next-step` |
| `features` | `auth`, `edit-profile`, `consents`, `profile-pdf`, `connect-source`, `start-assessment`, `shortlist-membership`, `send-invitation`, `respond-invitation` |
| `entities` | `session`, `meta`, `profile`, `qualification`, `skill`, `source`, `job`, `assessment`, `invitation`, `company`, `need`, `candidate`, `shortlist` |
| `shared` | `api` (client, errors, scope, generated types), `config`, `lib` (labels, formatting, document title), `ui` (UI kit) |

An entity holds the query options, query keys, request functions and small display components for one resource.
A feature is one user action with its mutation and form. A page composes them for one route.

## Routing

File routes live in `src/app/routes`; `routeTree.gen.ts` is generated by the router plugin (`autoCodeSplitting`, so
every route is a separate chunk). Route files are thin: search validation, guard, loader and the page component.

| Route | Guard | Search parameters |
| --- | --- | --- |
| `/` | Redirects to the role's home (`/candidate/overview`, `/employer/needs`) or `/login` | — |
| `/login` | Public | `redirect` (path starting with `/`), `reason=expired` |
| `/candidate/*` | Candidate session | `/candidate/skills`: `view` (`list`/`graph`), `node`; `/candidate/invitations`: `status` |
| `/employer/*` | Employer session | `/employer/candidates`: `needId`, `mode`, `specialization`, `grade`, `skill`, `fsp`, `page`, `shortlistId`; `/employer/candidates/{id}`: `needId`, `tab` (`match`/`skills`/`checks`), `shortlistId`; `/employer/invitations`: `status` |

- Search parameters are parsed with zod; a malformed value falls back to its default (`.catch(undefined)`) instead of
  reaching the API, so links with filters are shareable and survive reloads.
- `requireRole` revalidates the session on every protected navigation. Without a session it clears the cache and
  redirects to `/login?redirect=…` (with `reason=expired` if there was a session before); with the other role it
  renders «Раздел недоступен» with a link home.
- Loaders prefetch the data a page needs with `ensureQueryData`; pages read it with `useSuspenseQuery`. Pending,
  error and not-found states have shared components (`route-states.tsx`). Links preload on intent.
- After sign-in a candidate without a complete questionnaire lands on `/candidate/onboarding`, an employer without a
  complete company on `/employer/company`; otherwise the `redirect` target of the same role or the role's home.

## Data layer

- `shared/api/client.ts` creates the `openapi-fetch` client with `credentials: "include"` and an empty base URL.
  `requireData`/`requireOk` turn every non-2xx response into an `ApiError` carrying `status`, `code`, `requestId` and
  `details`; a success without the expected body is an error too.
- `describeError` maps errors to Russian titles and messages for people; `fieldErrors` maps validation `details` to
  form fields.
- **Cache scoping.** Every private query key starts with the scope `[role, actorId, companyId]` from the session
  (`scopeOf`, `useScope`). The cache is cleared on sign-in, logout, any `401` (handled centrally in `app.tsx`) and when
  the app shell sees another actor's session after a window focus.
- **Retries.** Queries retry once on transport errors and `5xx`, never on `4xx`; job polling retries twice; mutations
  never retry automatically. A default stale time of 10 seconds avoids refetch storms.
- **Jobs.** `useJob` polls `GET /api/v1/jobs/{id}` at the server's `pollAfterMs` (at least 250 ms), stops at a terminal
  state and calls back once; callers then invalidate what the job changed. Source cards resume polling from
  `activeJobId` after a reload.
- **Generated types** in `src/shared/api/generated/` come from `bun run codegen` (the TypeScript 7 generator in
  [`contracts/codegen`](../../contracts/codegen/README.md)); there are no hand-written DTO types.

## Mutations

- A mutation shows success only after the server confirms it and then updates the cache with the returned record
  (`setQueryData`) or invalidates the affected keys. Recoverable errors keep the user's input.
- **Idempotent commands** (start assessment, submit, create invitation) keep one key per intended command in a ref,
  reuse it when the same command is retried after a transport failure and drop it after any server answer.
- **Assessment draft:** the workspace autosaves 1.2 seconds after the last edit; the status line says «Черновик
  сохранён» only after the server acknowledges the save. Running checks and submitting first flush the draft; leaving
  with unsaved changes asks for confirmation (`UnsavedChangesGuard`, which also covers reloads).
- **Shortlist membership** is optimistic: the change appears at once, rolls back if the server rejects it, and
  every place showing the shortlist reads the same cache entry.
- **Conflicts** (`409`) on invitations and drafts refetch the canonical record and explain that the state changed.

## Forms

TanStack Form holds drafts; validators mirror the contract's limits for immediate feedback (required fields, salary
format and range, unique skills, at least one required requirement and one accepted source), and server validation
errors are mapped back to fields. Form models differ from DTOs where useful: salary is entered as text and converted
to whole rubles; `experienceMonths` keeps `null` (unknown) apart from `0`. Forms with unsaved changes block
navigation.

## Privacy boundaries in code

- Employer pages use only the anonymous projection; contacts come from the disclosure query and are rendered only
  in the disclosure card of the company that received them.
- Candidate self-view and employer views use different entities and components; nothing hides private data with
  CSS or a boolean flag.
- Demo links (`example.com/fixtures`) are shown as text, not as live links.

## Build-time behavior

| Code | Development | Production build |
| --- | --- | --- |
| Dev controls in the «Демо» dialog, «Вставить код из демо-ящика» | Present (lazy, `import.meta.env.DEV`) | Removed |
| Demo-stand notes and seed account hints on `/login` | Present | Only with `VITE_DEMO_STAND=1` |
| «Демо» dialog | Shown while `meta.mode` is `mock` | Shown while `meta.mode` is `mock` |

`scripts/check-bundle.ts` fails the build check if built JavaScript contains `/__mock__`, the mailbox or dev-control
strings, or the seed account addresses outside a `VITE_DEMO_STAND=1` build.

## Accessibility

Semantic landmarks and headings, a skip link, focus moved to the main region on navigation and after sign-in,
labelled controls with described errors, keyboard-operable lists and dialogs, a list alternative to the graph,
visible focus rings, 44 px standard control height, reduced motion honored by the tokens, and a navigation drawer
below 1024 px. The axe checks and narrow-screen tests are listed in [`TESTING.md`](TESTING.md).
