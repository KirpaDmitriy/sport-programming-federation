# С чего начать

Архив предназначен для агента, который реализует фронтенд нашей платформы на React, TypeScript и TanStack по FSD. Здесь собраны макеты, правила продукта, контракт под будущий Rust-бекенд, работающий локальный мок-сервер и проверяемый пример подключения API.

## Передать агенту

Распакуйте каталог рядом с рабочим репозиторием. Агент должен сначала проверить его текущее состояние и инструкции, затем прочитать:

1. [AGENTS.md](AGENTS.md).
2. [Полный промпт для реализации](agent/IMPLEMENTATION_PROMPT.md).
3. [Матрицу требований](docs/REQUIREMENTS_TRACEABILITY.md), [правила продукта](docs/PRODUCT_RULES.md) и [исправления макетов](docs/MOCKUP_CORRECTIONS.md).
4. [Спецификацию экранов](docs/SCREEN_SPECIFICATION.md), [архитектуру фронтенда](docs/FRONTEND_ARCHITECTURE.md) и [подключение API](docs/API_INTEGRATION.md).

Рабочий запрос агенту:

> Прочитай AGENTS.md и agent/IMPLEMENTATION_PROMPT.md из этого пакета. Проверь исходные материалы, запусти проверки пакета и реализуй фронтенд в frontend/ по плану. Используй контракт и настоящий локальный HTTP мок-сервер. Делай гранулярные коммиты, проверяй обе роли в браузере и сохраняй фактические результаты тестов. Не переноси ошибки из растровых макетов в код. Доведи обязательные пользовательские пути до рабочего состояния.

Промпт не требует конкретного провайдера или набора закрытых инструментов.

## Запустить проверку пакета

Нужен Bun 1.4.2 или новее: он устанавливает зависимости и исполняет код, у каждого пакета свой `bun.lock`. Зависимости устанавливаются из реестра или локального кеша; `node_modules` в архив не включены.

Из корня распакованного каталога:

```sh
bun install --cwd mock-server --frozen-lockfile
bun install --cwd tools/contract-codegen --frozen-lockfile
bun install --cwd frontend-reference --frozen-lockfile
bun scripts/verify-package.mjs
```

Для запуска API в отдельном терминале:

```sh
bun run --cwd mock-server start
```

Адрес: `http://127.0.0.1:4010`. Состояние: `/health`, параметры демонстрации: `/api/v1/meta`. Настройка пользователей и сценариев описана в [MOCK_SERVER.md](docs/MOCK_SERVER.md). Мок-сервер запускается локально; его служебный выбор пользователя не является готовой авторизацией для публичного размещения.

## Что уже согласовано

Кандидат выбирает желаемый грейд, но категория работодателя появляется только по результату проверки. GitHub дополняет профиль автоматически. История ФСП необязательна. Сильное свидетельство по одному навыку не подтверждает весь профессиональный уровень.

Работодатель описывает потребность и зарплату, находит обезличенных кандидатов, сохраняет подборку и отправляет конкретному человеку приглашение. Кандидат видит условия заранее. После принятия выбранные сведения получает только эта компания.

Основная реализация не включает чат, публикацию вакансий, самостоятельные отклики и регулярные задачи. Для них зафиксированы границы и выключенные возможности; агент не должен рисовать работающие кнопки без API.

## Что уточнено после проверки

- В настоящем ТЗ API и датасеты ФСП намеренно не предоставляются. Данные в пакете подготовлены нами и обозначены как синтетические.
- Десять изображений не покрывают все обязательные состояния. Регистрация, подтверждение почты, ошибки, история и другие переходы дополнены в текстовой спецификации.
- Установлены разные обозначения для подтверждённого грейда, отдельного навыка, наблюдения и пробела в требованиях.
- Исправлены предпросмотр приватности, состояние закладки в подборке и обещание отсутствующего чата.
- Зарплата в текущем контракте задаётся положительными целыми рублями за месяц до вычета налогов.
- Стаж, направление деятельности компании и регистрация работодателя учтены в данных.
- Генератор OpenAPI проверен запуском. Совместимый компилятор для генерации изолирован от TypeScript 7, на котором проверяется клиент.

## Граница готовности

Этот пакет позволяет начать реализацию фронтенда без ожидания рабочего Rust API. Сам полноценный интерфейс ещё должен быть написан агентом. Мок-сервер проверяет пользовательские переходы и форму обмена, но не доказывает реальную квалификацию кандидатов, качество матчинга или корректность анализа GitHub.

После подключения Rust нужно повторить проверки контрактов, прав доступа и браузерные сценарии. Отдельно потребуются реальные интеграции, оценка качества механик и итоговая сдача хакатона. Эти ограничения явно перечислены в [реестре решений и рисков](docs/DECISIONS_AND_RISKS.md).
